CivicSetu Architecture Audit

A read of both repositories before any change: what exists today, what blocks the 1,000-concurrent-user target, and a phased path to a production platform on Azure. No file in either repository has been modified.

Summary

  • There is one backend today and no BFFs. civicsetu-v1 is a Django modular monolith: 13 apps, 68 REST endpoints, about 8,500 lines of Python outside tests and migrations, and 237 tests. The website is built into the same Django process and served from it.
  • The CIVIC mobile app isn't connected to the backend yet. By default it opens the CIVIC web app in a WebView, and that web app keeps complaints, tracking codes and sign-ins in browser storage. Its source (src/ and mobile/src/) isn't in the repository; only compiled bundles are.
  • main is missing critical security fixes. They sit on the unmerged branch fix/security-hardening along with the move to PostgreSQL. main has since gained a separate UI redesign, so the two lines have diverged.
  • Supabase isn't in use. The branch targets PostgreSQL 18 on the development PC. Your only Supabase project is paused and located in Tokyo, far from Indian users and from Azure Central India.
  • It can't run on more than one server yet. Uploads go to local disk, rate limits are counted in each process's memory, logs go to a local file, and there are no health checks, containers or pipelines.
  • The foundations are good. Business logic lives in service classes, complaint visibility rules are in one module (apps/complaints/scoping.py), and the October data ledger lists about 1,230 rows. A gradual migration is practical.
Recommendation

Build CivicSetu as nine domain microservices and two BFFs: Identity, Grievance, Department & Routing, Triage, Media, Notification, Feedback, Reporting and Audit. Each owns its own data schema, API, pipeline and scaling, talks to others through versioned APIs and events, and is carved out of today's Django app one at a time behind the BFFs, so the product keeps working throughout. A seven-layer customization model lets you change business rules, features, settings, themes, providers and infrastructure without touching code, or with a change to one small place. Cost rises to about $420–880 a month in production, from $280–590 for the earlier four-deployable design.

Needed from you before Phase 0
  1. Push the CIVIC source code. Commit the web app's src/ and the mobile app's mobile/src/ to CIVIC--Powered-by-CivicSetu. Its own docs/BASELINE.md says the work happened in a folder without git. Without the source, the mobile app can't be changed or pointed at a BFF.
  2. Choose which UI to keep when merging. main has the kesari palette and guided report flow (a45d389, today). design/premium-ui has the calm petrol and sage restyle (443b361). Both rewrite the same stylesheets. The backend fixes merge either way.
  3. Choose the database host. (a) A new Supabase Pro project in Mumbai (ap-south-1); the Tokyo project can't change region. (b) Azure Database for PostgreSQL Flexible Server in Central India, which keeps the database inside the Azure network. I recommend (a) because it matches your brief and its trade-offs are manageable (section E).
  4. Approve the revised shape: nine services, two BFFs and the customization layers in section C, at the higher cost in section G.
  5. Product call on AI triage. docs/AI_REMOVAL_PLAN.md removes the ML models; commit 69f94a6 on the branch turns them back on ahead of the keyword rules. Either works; pick one so code, tests and docs agree.

B.3 Performance assessment

  • Filing a complaint does everything in one request and one transaction: AI triage (twice if the first call fails), one notification insert per officer in the category (or per super admin), Pillow checks, each image written twice, history rows and an audit row. The database connection is held while uploads are processed.
  • Password reset sends SMTP inside the request with a 10-second timeout, blocking a worker.
  • Analytics run one COUNT per status, category and priority (6 + 10 + 4 queries) and loop over every resolved complaint in Python to average resolution time.
  • Search uses icontains on four text columns, a full table scan. Fine at 38 rows, slow at 100,000.
  • Redundant indexes: tracking_code and department slug each have a unique index plus a second plain index.
  • The deployment guide runs 4 sync Gunicorn workers with a 120-second timeout, so a few slow uploads block the whole server. Its NGINX limit of 10 MB rejects the 25 MB videos the API allows.
  • The website's axios client has no timeout, and concurrent 401s race the token refresh (A.7).
  • JWT tables only grow: 377 outstanding and 125 blacklisted rows in October, with no cleanup job.
  • The ML models aren't a bottleneck. They're 3–7 KB and load once per process.

B.4 Technical debt and coupling

  • Diverged branches and committed build output: static/react, CIVIC dist/, a 2.4 MB mobile bundle and a 900 KB zip of docs are in git, while the CIVIC source isn't.
  • Department routing by keyword: scoping.py decides which officers see a complaint from words like “WATER” in the department name. Renaming “Water Supply” to “Jal Board” would hide water complaints from its own officers. The same category mapping is repeated three more times in create_complaint, and users.department is free text that duplicates department_authorities.
  • create_complaint can save the category TRAFFIC, which isn't one of the allowed choices.
  • Duplicated routes: notifications at two paths with different response shapes, status changes at two paths. NotificationService lives in the authority app.
  • AI direction conflict between docs/AI_REMOVAL_PLAN.md and commit 69f94a6.
  • Leftovers from academic reviews: REVIEW_PHASE and toggle_review_mode.py have no effect on the backend.
  • Repository clutter: PDFs, report generators and model files at the root; the same images in static/, static/images/ and frontend/public/.
  • The website mixes JavaScript and TypeScript (App.jsx, Landing.jsx) and has no tests.

C.2 Rules that keep the services independent

Without these rules, separate services slowly turn into a distributed monolith: they still have to be released together, only now over a network.

  • Each service owns its data. No service reads or writes another service's schema; each one gets a database role that can only see its own.
  • No foreign keys between services. They refer to each other by public UUID.
  • At most one synchronous hop between domain services per request (Grievance asking Triage at filing time, with a fallback). Anything else a service needs comes from a local copy kept current by events.
  • Each service owns a versioned API (/v1) described in OpenAPI. A breaking change ships as /v2 next to /v1 until every caller has moved.
  • Events leave only through each service's outbox, and every consumer ignores duplicates.
  • One shared technical library, no shared business code. The library handles tokens, errors, logging, tracing, configuration, outbox and health checks; models and rules never cross services.
  • Each service has its own pipeline, image, revisions, scale rules, managed identity, database role and configuration namespace. A service deploys alone when its contract tests pass.

Guardrails on every change

  • Validated against a schema, with a clear reason when rejected (for example, a category with no department).
  • Versioned with who, when and what, and a one-step return to any earlier version.
  • Audited through the Audit service.
  • Tried in staging first when you want: export a configuration bundle from staging and import it into production.
  • Flags have an owner and an end date, so finished experiments get removed instead of piling up.

C.12 Trade-offs

Eleven deployables cost more to run than four (section G), dashboards built from events can lag a few seconds behind the live data, and a bug can span several services. The plan offsets this with one service template, distributed tracing from the first extraction, contract tests that gate every deploy, and per-service runbooks.

D.2 Considered and not chosen

  • API Management: the BFFs already handle authentication and response shaping, and Front Door handles edge routing and rate limits. Add it later if partner systems, such as other municipal software, need a managed external API.
  • AKS: becomes worth it around 20–30 services or when you need service-mesh features. Container Apps already gives per-app revisions, scale rules and mutual TLS.
  • Dapr: built into Container Apps, but left out at first to keep each service plain Django that runs the same on a laptop.
  • App Service: fine for web apps, weaker for queue-driven consumers and jobs.
  • Application Gateway WAF v2: regional and about $250 a month before traffic; Front Door covers TLS, WAF and the edge for less.
  • Event Hubs or Kafka: streaming platforms for far larger volumes than CivicSetu produces.
  • Azure DevOps: code and issues are on GitHub.
  • Terraform: Bicep is native to Azure and has no state file to secure; Supabase is managed through its CLI. Terraform remains an option if you later want one tool for both.

E.2 How the split happens

  1. Schemas first, inside today's app (Phase 2). Create the nine schemas and move each table with ALTER TABLE … SET SCHEMA, which changes only metadata and takes milliseconds. Django finds tables through each role's search_path, so table names in code don't change.
  2. Cut foreign keys between services. Add UUID reference columns, backfill them, switch the code, then drop the old foreign-key columns in a later release.
  3. One role per service, allowed only on its own schema. While the old app still runs, its role keeps access to the schemas it hasn't handed over.
  4. On extraction, the new service connects with its own role and the old app's access to that schema is removed.
  5. Own database when needed: pg_dump --schema=<service> into a new database and change one connection secret. Likely first candidates are Grievance and Reporting.

E.4 Database architecture

E.5 Connection pooling

  • Gunicorn gthread with 2 workers × 2 threads gives at most 4 connections per replica. About 18 replicas plus relays and jobs come to roughly 90 client connections, which the pooler multiplexes onto far fewer server connections. Supabase Medium compute gives comfortable headroom; confirm the limits for the size you pick.
  • Django settings: DISABLE_SERVER_SIDE_CURSORS = True (required in transaction mode), CONN_MAX_AGE = 60 with health checks, connect_timeout = 3, sslmode = verify-full with Supabase's CA certificate.
  • search_path and statement_timeout are set on each role, because the transaction pooler doesn't pass start-up options.
  • Migrations run from each service's pipeline before its new revision gets traffic, never at container start.

E.6 Roles and new tables, Grievance as the example

Every service gets the same pattern. Django migrations create the tables; the SQL is here for review.

E.7 Index changes

  • grievance.complaints: add (citizen_public_id, created_at DESC), (department_public_id, status, created_at DESC) and (officer_public_id, status).
  • notify.notifications: (recipient_public_id, is_read, created_at DESC).
  • pg_trgm GIN indexes for complaint search on title, description and address.
  • Drop the redundant idx_complaint_tracking and idx_dept_slug.
  • Indexes are created with AddIndexConcurrently so tables stay writable.

E.8 Moving the data

  1. Rehearse (Phase 3). Restore the local PostgreSQL 18 database into a scratch Supabase project. Restoring an 18 dump into 17 isn't officially supported; if pg_restore rejects it, use Django dumpdata and loaddata. Check every table's row count against the October ledger and reset sequences.
  2. Media. Copy media/ into the private container with azcopy and compare SHA-256 hashes.
  3. Cutover (Phase 14). Pause writes with a maintenance page, take a verified backup, move the data, verify, then switch connection secrets. At this data size it takes minutes.

E.9 Backup and recovery

  • Supabase Pro daily backups kept 7 days; point-in-time recovery in production.
  • Weekly pg_dump per schema to an immutable Blob container, kept 35 days, so one service can be restored without touching the others.
  • Blob soft delete for 14 days and versioning on the media container.
  • Targets: at most 15 minutes of data loss with PITR (24 hours without), service back within 4 hours.
  • A restore drill into staging every quarter, timed and recorded.

Phase 12Load testing against agreed targetsNo capacity claim until this passes.
Workload model
1,000 concurrent sessions, each acting every 15–30 s with 3–5 API calls per action: about 100–330 requests per second steady, 2× peak for 10 minutes, 2-hour soak. Mix: 45% reads, 20% notification polls, 10% public tracking, 10% sign-in and refresh, 8% complaint creation, 3% with a 1–3 MB photo, 4% officer updates. These are assumptions to check against real analytics
Acceptance criteria
  • Reads: p50 under 150 ms, p95 under 400 ms, p99 under 1 s, measured at the BFF
  • Writes: p95 under 800 ms, excluding file transfer
  • Errors under 0.5%, excluding intended 429s
  • CPU under 70% per replica at steady load; memory growth under 10% over the soak
  • Pooler client connections under 70% of the limit; no query over 100 ms at p95
  • Event to notification under 30 s at p95; every outbox count equals delivered plus dead-lettered
  • No request makes more than one synchronous hop between domain services (checked in traces)

Rollback rules for every phase

  • Changes are additive or behind a flag; each phase ends with a tag such as phase-6-done.
  • Until a module is deleted from today's app, moving a route back in the BFF routing table undoes its extraction.
  • Database changes follow expand, migrate, contract. Nothing is dropped or renamed in the release that stops using it.
  • No destructive database operation without your explicit approval and a verified backup.
  • Each service keeps its previous revision for 24 hours, so a rollback is a traffic switch for that service alone.
  • No production deployment without your explicit approval.
